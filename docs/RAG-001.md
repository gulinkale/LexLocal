# RAG-001 — Workspace-Scoped Deterministic Retrieval and Evidence Persistence

## Status

**IN PROGRESS — STEPS 1–7 COMPLETE; HUMAN STAGED-DIFF REVIEW OPEN**

Repository evidence and the approved human decisions define an implementation-ready
M1 plan. The Application contracts/ranker, transaction-neutral SQLite persistence,
and preparation/staging orchestration are complete; no dependency or later-step
behavior has been added.

## Purpose

Retrieve exact eligible ACTIVE-index chunks for the sole active workspace and a
QA-request-owned document scope, generate one compatible ephemeral query embedding,
compute deterministic local cosine top-K results, and stage the retrieval run, exact
generation snapshot, and ranked evidence through a caller-owned Unit of Work.

RAG-001 ends at ranked persisted evidence. Evidence-sufficiency classification, answer
generation, citation validation, presentation labels, and UI behavior remain owned by
later tickets.

## Completion Condition

RAG-001 is complete when one anonymous synthetic QA request can resolve its exact active
document/version scope, prove a single compatible ACTIVE-generation cohort, embed its
exact query once through the existing `EmbedQuery`, deterministically rank valid local
vectors, and stage one complete retrieval/evidence graph that the caller can atomically
commit or roll back. Repeating the same committed QA request reuses the compatible
persisted identities; isolation, corruption, empty-result, and provenance behavior are
all proven without an ORM, vector database, query-vector persistence, answer generation,
or cloud fallback.

## Scope

- Support persisted QA retrieval only; every `RetrievalRun` belongs to an existing QA
  request in the active workspace.
- Treat existing `qa_scope_versions` rows as the authoritative exact document/version
  scope and allow an optional logical-document filter only to narrow that scope.
- Resolve exactly one eligible ACTIVE index generation for every included active
  document version and require the complete resolved set to form one exact embedding
  compatibility cohort.
- Select one deterministic representative ACTIVE generation and reuse the existing
  `EmbedQuery` path to create one ephemeral query vector for that cohort.
- Load and strictly validate the complete scoped chunk/vector/provenance graph.
- Compute cosine similarity locally with deterministic standard-library arithmetic.
- Apply the configured minimum-similarity threshold, deterministic ranking, and top-K.
- Stage the retrieval run, exact generation set, and full-text ranked evidence snapshots
  through the existing sensitive-payload and caller-owned UoW boundaries.
- Reuse a complete compatible committed retrieval for the same QA request and fail
  closed on ambiguous or conflicting persisted state.

## Explicit Non-Goals

- `ANALYSIS_SECTION` retrieval or a standalone retrieval owner.
- Creating chats, QA requests, question messages, or QA scope snapshots.
- RAG-002 evidence-sufficiency/confidence decisions.
- Answer generation, prompt construction, citation validation, evidence display codes,
  source opening, CHAT behavior, or UI.
- Query-vector persistence, chunk-embedding writes, index creation, model selection,
  index activation, or changes to INDEX/EMBEDDING lifecycle ownership.
- ORM, vector database, SQLite vector extension, NumPy dependency, retrieval cache, ANN,
  streaming, worker/retry framework, or generic vector-search/provider framework.
- Cloud/network fallback, production crypto, key lifecycle, or claims that the insecure
  development codec provides confidentiality.
- Schema changes beyond the approved migration 004 fields and relation.

  ACTIVE document version, ACTIVE index generation, matching workspace, and matching
  version/generation ownership.
- `src/lexlocal/domain/identifiers.py` already provides distinct `RetrievalRunId` and

  chunk, page, locator, and model IDs required by this ticket. It does not yet provide a
  `QaRequestId`, although the repository convention requires typed UUID identities at

- `src/lexlocal/application/ports/indexing.py::PersistedIndexGeneration` exposes an
  immutable `IndexGeneration` plus validated lifecycle timestamps. Its generation owns
  the exact workspace, document version, processing job, embedding model, chunking
  profile, normalization profile, dimensions, and state.
- `IndexGeneration` is a frozen Domain value. The existing SQLite INDEX repository
  changes only lifecycle state/timestamps during activation/archive; it does not rewrite
  generation ownership or compatibility metadata. A persisted generation ID can
  therefore reconstruct the historical compatibility metadata without duplicating
  model/dimension/profile/dtype columns in the new relation.
- The schema stores `vector_dtype='float32'` on `index_generations`; one ACTIVE
  generation per document version is protected by `ux_version_one_active_index`.
- `src/lexlocal/application/ports/embeddings.py::EmbeddingCompatibility` carries exact
  generation/model/profile/dimension/dtype/unit-normalized metadata. `QueryEmbedding`
  contains one immutable normalized vector and no persistence behavior.
- `src/lexlocal/application/embeddings.py::EmbedQuery` requires the sole active
  workspace and one explicit ACTIVE `PersistedIndexGeneration`, validates the exact
  ready provider/model and dimensions, sends the exact query as one input, and returns
  the vector without opening a UoW.
- `src/lexlocal/infrastructure/persistence/sqlite_embedding_repository.py` defines the
  canonical `lexlocal-f32-le-v1` little-endian float32 payload and exact
  workspace/chunk/model/dimension/dtype security context. Retrieval must reuse its
  representation and validation rules rather than introduce a second vector format.
- The `chunks` table stores deterministic `document_order`, exact page/locator/version
  ownership, protected full chunk text, and source offsets. The `embeddings` table stores
  one normalized float32 vector per chunk with generation/model metadata.
- `qa_scope_versions` already stores an immutable exact QA document/version snapshot.
  RAG must validate it; it must not introduce a parallel document-scope table.
- `retrieval_runs` already stores QA ownership, protected query, embedding model,
  effective top-K, candidate count, retrieval-policy version, and timestamp, but lacks
  the effective minimum-similarity value.
- `evidence_items` already stores `EvidenceItemId`, rank, score, chunk/locator/document/
  version/page provenance, a document-name snapshot, a protected excerpt, availability,
  and timestamp. The actual schema has no `evidence_code` column.
- Existing `UnitOfWork` and `SQLiteUnitOfWork` establish caller-owned transactions.
  Repositories do not commit or roll back; concrete repository properties are added only
  together with their real SQLite implementation.
- `AppSettings` owns environment loading and bounded operational settings. Bootstrap is
  the only layer allowed to compose concrete SQLite/security/provider implementations.
- The declared project dependencies are Foundry Local SDK and PySide6. Normalized cosine
  can be computed as a dot product with the standard library; NumPy is unnecessary.
- Existing architecture tests forbid Application SQLite/raw SQL/concrete Infrastructure
  dependencies and permit Bootstrap composition plus Infrastructure implementation of
  Application-owned ports.

## Frozen Decisions

1. RAG-001 supports persisted QA retrieval only. Every run references an existing
   same-workspace QA request. `ANALYSIS_SECTION` and standalone owners are rejected and
   receive no new port, ID, repository path, or schema support.
2. Step 1 adds exactly one `QaRequestId` using the existing typed UUID identifier
   implementation because this public owner identity is immediately required by RAG.
   It adds no chat/QA entity, lifecycle, repository, or creation use case.
3. `qa_scope_versions` is the authoritative exact logical-document/version scope. An
   omitted optional filter means the full QA snapshot; a provided non-empty set of
   `DocumentId` values may only select members of that snapshot. Unknown, empty,
   cross-workspace, duplicate, inactive, archived, deleted, or otherwise invalid scope
   relationships fail closed. RAG never silently widens or reduces the requested scope.
4. An eligible retrieval source requires the exact same active workspace; ACTIVE logical
   document; ACTIVE document version from the QA snapshot; exactly one ACTIVE index
   generation for that version; complete matching chunks and embeddings; and valid
   workspace/version/generation/page/locator/model/profile/dimension/dtype/unit-normalized
   ownership. Missing or corrupt relationships are errors, not exclusions.
5. All resolved generations must belong to one compatibility cohort. Cohort equality
   requires the same workspace, exact `LocalModelId`, chunking profile, normalization
   profile, positive dimensions, `float32`, and unit-normalized representation.
   Generation/document identities may differ. Any incompatibility fails the whole
   retrieval before query inference, scoring, or persistence; M1 has no partial or
   reduced-scope fallback.
6. The explicit `EmbedQuery` representative is chosen from the proven cohort by
   canonical ascending `DocumentId`, then `DocumentVersionId`, then
   `IndexGenerationId`. Database order, insertion order, timestamps, retrieval/evidence
   IDs, and incidental row order cannot affect the choice.
7. RAG calls the existing `EmbedQuery` exactly once with that representative and the
   exact query text. The normalized query vector may be reused only for the proven exact
   cohort and remains ephemeral. It is never written to SQLite or included in logs or
   public representations.
8. Stored vectors and query vectors are normalized, so cosine similarity is computed as
   an explicit local dot product. Inputs must have matching positive dimensions and
   finite values; the resulting score must satisfy the existing `SimilarityScore`
   contract. RAG adds no alternate normalization or vector serialization.
9. Candidate ordering is similarity descending. Exact score ties use canonical
   ascending `DocumentId`, `DocumentVersionId`, `IndexGenerationId`, chunk
   `document_order`, and `ChunkId`. The tie key applies only to exact score equality;
   timestamps, row/insertion order, `RetrievalRunId`, and `EvidenceItemId` never affect
   ranking.
10. `LEXLOCAL_RETRIEVAL_TOP_K` is an operational setting with M1 default 5 and inclusive
   range 1 through 20. When fewer candidates remain, all remaining candidates are
   returned without error. The effective value is persisted in `retrieval_runs.top_k`
   and is not index compatibility metadata.
11. `LEXLOCAL_RETRIEVAL_MIN_SIMILARITY` is an operational setting with M1 default 0.0
    and inclusive range -1.0 through 1.0. A candidate passes when
    `score >= min_similarity`. Filtering occurs before ranking/top-K. The effective
    value is persisted; it is neither model confidence nor evidence sufficiency and is
    not index compatibility metadata.
12. `candidate_count` is the number of valid scoped chunk embeddings for which cosine
    was actually computed, after all scope/state/ownership/compatibility/integrity
    validation and before threshold/top-K. Below-threshold and non-top-K candidates
    count; corrupt/incompatible candidates fail instead of disappearing. Evidence row
    count is the final returned evidence count.
13. No eligible ACTIVE generation produces a sanitized `NoEligibleIndex` Application
    failure and no successful run. An ACTIVE generation with zero, missing, incomplete,
    corrupt, or incompatible embedding state produces a sanitized integrity failure.
    Integrity failures are never converted into successful empty results.
14. When valid candidates were scored but none passes the threshold, retrieval succeeds
    and stages one run with exact owner/scope/generation/configuration, its nonzero
    `candidate_count`, and zero evidence rows.
15. Every selected evidence item snapshots the exact full chunk text. RAG performs no
    truncation, normalization, summarization, or excerpt selection. The mandatory
    excerpt crosses `SensitivePayloadCodec`; the validated document name, version
    number, page number, chunk ID, locator ID, and remaining schema provenance are
    retrieval-time snapshots, not later reconstruction from mutable live display data.
16. `EvidenceItemId` is the stable persisted identity and `EvidenceRank` is the
    authoritative run-local order. RAG does not add `evidence_code`; later CHAT or
    presentation may derive `E1`, `E2`, and similar labels from rank without using them
    as database identity.
17. One QA request owns one logical persisted retrieval. A new QA request receives a
    new injected `RetrievalRunId` and injected `EvidenceItemId` values; IDs are not
    content hashes and do not affect logical ranking.
18. A retry first checks for an existing committed run. It reuses that run and the same
    evidence IDs only when the exact QA scope, exact persisted generation set, query,
    model/cohort, effective top-K/threshold, policy version, candidate count, evidence
    ranks/scores, and protected snapshots reconstruct as complete and compatible. A
    conflict or multiple existing runs fails closed; RAG never replaces the run or
    creates a second successful one. If the prior caller-owned transaction rolled back,
    no committed run exists and retry may recompute with new transient IDs. Fresh
    retrieval requires a new QA request.
19. Migration 004 may only add the effective minimum-similarity field and the minimal
    `retrieval_run_generations` relation. The latter snapshots the exact generation IDs
    used by a run, including successful zero-evidence runs; it does not replace or copy
    `qa_scope_versions` and does not duplicate immutable generation compatibility
    columns.
20. Retrieval preparation performs scope resolution, query inference, vector decoding,
    validation, and ranking outside the final write transaction. The complete immutable
    registration is then staged through a caller-owned active UoW. RAG and its repository
    never open a second connection, commit, or roll back. The higher QA/CHAT orchestration
    retains authority to atomically commit or roll back scope, retrieval, evidence,
    answer, and citations.
21. The persistence repository uses one atomic guarded QA-owner insert/check under the
    caller transaction and treats multiple runs for one QA request as corruption. No
    uniqueness index beyond the approved migration scope is added.
22. RAG owns neither index/model selection nor lifecycle transitions. It does not create,
    update, activate, archive, repair, or delete generations, chunks, or embeddings.
23. RAG-001 does not classify sufficiency, generate answers, create citations, or turn
    similarity into confidence. Those responsibilities remain downstream.
24. The authoritative baseline is brute-force SQLite loading plus local standard-library
    scoring. No cache or optimized provider is implemented in M1 RAG-001.

## Security and Data Boundaries

- Query text, chunk text, full evidence excerpts, document display names, and vectors are
  sensitive. They do not appear in exceptions, logs, IDs, test names, representations,
  diagnostics, or final reports.
- Existing chunk/vector payloads are decoded through their existing exact
  `SensitivePayloadCodec` contexts. Query and evidence snapshots are encoded through
  deterministic contexts bound to workspace and their stable owning run/evidence IDs.
- No raw key enters Domain or Application. `WorkspaceKeyReference` and the configured
  codec remain the only security boundary.
- Development/test may use the existing insecure codec only with anonymous synthetic
  fixtures under its four warnings: DEVELOPMENT ONLY, SYNTHETIC FIXTURES ONLY, NOT
  RELEASE SAFE, and NOT FOR REAL USER DOCUMENTS.
- Production composition remains fail-closed before sensitive retrieval work. No secure
  provider is invented and no development plaintext is described as encryption or
  confidentiality.
- Cross-workspace mismatch is rejected before existence, format, query, or identity
  details can leak. All persistence/provider/codec errors are translated to sanitized
  Application errors without chained sensitive causes.

## Persistence and Transaction Boundaries

Preparation path:

```text
ActiveWorkspaceScope
→ existing QA owner + qa_scope_versions
→ optional DocumentId narrowing
→ exact ACTIVE version/generation resolution
→ exact compatibility-cohort proof
→ deterministic representative PersistedIndexGeneration
→ existing EmbedQuery (one ephemeral vector)
→ exact eligible chunk/vector/provenance load and decode
→ candidate_count
→ local cosine scores
→ inclusive threshold
→ deterministic ranking/ties
→ top-K
→ immutable retrieval registration with injected IDs/time
```

Caller-owned persistence path:

```text
caller opens UnitOfWork
→ repository revalidates QA scope + exact ACTIVE generation snapshot
→ compatible committed same-QA run is reused, or complete new graph is staged
→ retrieval_runs + retrieval_run_generations + evidence_items
→ caller stages later answer/citation work
→ caller alone commits or rolls back
```

No query inference, vector scoring, or payload preparation is performed while RAG owns
a write transaction. RAG reports no committed success on behalf of the caller.

Current migration sequence is 001, 002, 003, 004. Step 2 added:

  - `retrieval_run_generations` with only `retrieval_run_id`, `workspace_id`, and
    `index_generation_id`; a composite primary key for run/generation; and composite
    workspace-safe foreign keys to `retrieval_runs(id, workspace_id)` with
    `ON DELETE CASCADE` and `index_generations(id, workspace_id)` with
    `ON DELETE RESTRICT`. Updates remain restricted. The primary key supplies the only
    required index; no unrelated index is added.

The generation relation contains no document/version/model/profile/dimension/dtype
copies. Joining its exact generation ID to immutable `index_generations` reconstructs
those values; joining that generation's document version to `qa_scope_versions` proves
that it belongs to the authoritative QA scope. Repository validation requires exactly
one generation row for each resolved scoped version and no extra row, including when
there are zero evidence items.

No applied migration is rewritten. No evidence-code column, owner schema, generic scope
table, vector index, unrelated index, or cleanup is authorized. Migration tests must
prove clean creation, forward upgrade, constraints, foreign keys, and zero-evidence
generation snapshots.
