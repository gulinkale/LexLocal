## Purpose

Evaluate one complete, validated RAG-001 QA retrieval with the existing local Foundry
chat model and classify it as exactly one Domain `EvidenceSufficiency` state:

- `SUFFICIENT`;
- `RELATED_BUT_INSUFFICIENT`; or
- `INSUFFICIENT`.

The local model performs only a strict per-evidence semantic-relation assessment.
Application code validates that assessment and applies the frozen deterministic
aggregation policy. The model never chooses the final sufficiency state.

RAG-002 returns one immutable, versioned, CHAT-consumable result containing the final
state, ordered validated relations, policy-approved related evidence, exact verifier
and contract identity, and safe aggregate diagnostics. It does not retrieve, rank,
persist, answer, cite, or complete a QA request.

## Completion Condition

RAG-002 is complete when repository evidence proves that the exact local verifier
assesses every selected `E{rank}` once, malformed output fails or succeeds only through
the one permitted constrained repair, Application aggregation implements the frozen
truth table exactly, warning coverage and contradictions veto `SUFFICIENT`, related
evidence preserves RAG order, CHAT can consume the result without recalculation, and
all security, offline, regression, quality, Git, and human-review gates pass.

Before final completion, the CHAT-owned historical snapshot must have an approved
faithful persistence shape. RAG-002 itself still adds no repository or Unit of Work.

## Frozen Decisions

### 1. Positive semantic support requires the local verifier

- Similarity, rank, selected count, candidate count, provenance, diversity, and
  coverage cannot independently establish semantic support.
- Zero selected evidence returns `INSUFFICIENT` without invoking the verifier.
- Non-empty evidence without at least one validated `SUPPORTS` relation is at most
  `RELATED_BUT_INSUFFICIENT`.
- Any `READY_WITH_WARNINGS` generation vetoes `SUFFICIENT`.
- RAG-002 reuses the existing process-owned exact READY Foundry chat model/runtime
  behind a dedicated Application-owned semantic-verifier port.
- There is no cloud, network, alternate-model, or general-knowledge fallback.
- The verifier classifies evidence relations only. It never outputs or overrides
  `EvidenceSufficiency`.

### 2. Exact verifier contract

The relation vocabulary is exactly:

- `SUPPORTS`: the item contains question-answering information and belongs to a
  coherent, non-conflicting selected evidence set that provides enough information
  to answer the exact question. Negative, corrective, or alternative direct answers
  remain `SUPPORTS` and must not be treated as contradictions merely because they
  differ from an assumed answer;
- `RELATED_ONLY`: the item explicitly concerns the question-relevant subject or fact,
  but does not provide enough information to answer the asked value or property under
  the complete selected evidence set;
- `CONTRADICTS`: the item is question-answering evidence that genuinely conflicts
  with another selected evidence item about the same question-relevant fact. Every
  item participating in that genuine conflict is `CONTRADICTS`; neither side is
  arbitrarily treated as the expected or correct answer;
- `IRRELEVANT`: the item provides no meaningful question-answering information and
  does not explicitly concern the question-relevant subject or fact; superficial
  lexical overlap alone is insufficient to make it `RELATED_ONLY`.

Every `E{rank}` is assessed against the exact question in the context of the complete
supplied selected evidence set. A genuine conflict takes precedence over otherwise
question-answering support so every conflict participant receives `CONTRADICTS`.
After ruling out `SUPPORTS` and `CONTRADICTS`, explicit concern with the
question-relevant subject or fact is `RELATED_ONLY`, including a different property or
an explicit absence of the asked value. `IRRELEVANT` applies only when that explicit
link is absent.

The versioned M1 structured output is exactly one top-level `assessments` array. Each
item has exactly these fields:

```json
{
  "evidence": "E1",
  "relation": "SUPPORTS"
}
```

The full output therefore has this shape:

```json
{
  "assessments": [
    {"evidence": "E1", "relation": "SUPPORTS"}
  ]
}
```

- Every supplied `E{rank}` appears exactly once.
- Input assessment order is not authoritative. After validating exact one-to-one label
  coverage, Application orders the typed relations by the existing RAG `EvidenceRank`.
- Missing, duplicate, unknown, malformed, or extra assessments and any additional
  top-level or item field are invalid.
- The verifier must not emit sufficiency, confidence/probability, authoritative
  source metadata, free-form rationale, or any other field.
- The model receives the exact question and exact selected excerpts labelled only by
  `E{rank}`. Application-controlled identity/provenance remains outside model output.

### 3. Deterministic Application aggregation

Apply this precedence exactly:

1. Invalid, incomplete, corrupt, cross-scope, or incompatible input is an operational
   or integrity failure.
2. Zero selected evidence is `INSUFFICIENT`, with no verifier call.
3. For non-empty evidence, validate exactly one relation per RAG rank before
   aggregation.
4. Any `CONTRADICTS` relation vetoes `SUFFICIENT`.
5. Any `READY_WITH_WARNINGS` generation vetoes `SUFFICIENT`.
6. All-READY coverage plus at least one `SUPPORTS` and no `CONTRADICTS` is
   `SUFFICIENT`.
7. Otherwise, any non-`IRRELEVANT` relation is
   `RELATED_BUT_INSUFFICIENT`.
8. All `IRRELEVANT` is `INSUFFICIENT`.

Similarity, rank, counts, diversity, retrieval threshold, top-K, and score margins do
not override this mapping. They remain RAG facts, not confidence or sufficiency rules.

### 4. Policy-approved related evidence

For `RELATED_BUT_INSUFFICIENT`:

- include every `SUPPORTS`, `RELATED_ONLY`, and `CONTRADICTS` assessment;
- exclude every `IRRELEVANT` assessment;
- retain the exact original RAG `EvidenceItemId` and `EvidenceRank` order;
- never rerank, renumber, duplicate, widen, replace, or invent evidence.

`INSUFFICIENT` approves no related evidence. `SUFFICIENT` exposes the complete
validated relation set but does not reuse the related-evidence field as a second
generation-context selector; CHAT uses the exact RAG result for grounded generation.

### 5. Identity, versioning, and reproducibility

- Exact resolved verifier-model identity, verifier-contract version, evidence-policy
  version, and CHAT answer-generation model identity are logically distinct.
- The evidence-policy version identifies and immutably binds one exact tuple:
  verifier model identity, verifier contract, existing provider invocation profile,
  relation vocabulary and semantics, aggregation precedence, coverage rule, repair
  rule, and related-evidence semantics.
- The corrected M1 verifier invocation profile uses the existing exact configured
  local `ChatInferenceProvider` with `temperature = 0.0` and repository-defined
  `random_seed = 0`. These two call-scoped controls are applied only for verifier
  inference and restored afterward, so ordinary CHAT inference behavior is unchanged.
  No other inference setting is introduced.
- The clarified relation semantics and corrected invocation profile are identified by
  immutable verifier contract `evidence-relations-v2` and evidence policy
  `evidence-policy-v2`. Qualification remains authoritative; this profile does not
  claim theoretical bit-level determinism.
- Any later verifier-model, semantic, temperature, seed, sampling, token, or other
  invocation-profile change requires a new policy version and contract review.
- Application mapping from a validated relation set to final state, related evidence,
  and diagnostics is strictly deterministic.
- Repeated anonymous synthetic qualification cases test relation and final-policy
  stability under the same exact resolved model/contract/profile.
- RAG-002 does not claim byte-for-byte deterministic raw model output and does not run
  duplicate inference inside one evaluation merely to check stability.

### 6. Failure, one repair, and cancellation

- Unavailable/non-READY verifier, invocation failure, malformed output, invalid
  assessment coverage, cancellation, or provider/runtime error is an operational
  failure, never an insufficient-evidence decision.
- One invalid initial output permits at most one constrained repair call using the
  same exact provider/model, contract version, question, evidence labels/excerpts,
  relation vocabulary, and output schema.
- A second invalid result fails. No silent coercion, extraction, deduplication,
  relation invention, partial acceptance, or model substitution is allowed.
- Cancellation is cooperative and checked before work, immediately before and after
  each permitted inference, before repair, and before returning the final decision.
- An in-flight provider call is not forcibly interrupted. Its result is discarded if
  cancellation is observed when the call returns.
- Errors, representations, logs, diagnostics, and test IDs contain no question,
  excerpt, prompt, raw output, evidence/document/source IDs, provider object,
  exception string, path, URI, environment value, secret, or sensitive payload.

### 7. Persistence and CHAT handoff

- RAG-002 owns no repository, UoW property, commit, rollback, cache, or persistence
  write.
- Its immutable result exposes everything CHAT needs without recalculation:
  final `EvidenceSufficiency`, exact policy identity, exact verifier/contract identity,
  ordered validated relations aligned to existing `EvidenceItemId`/`EvidenceRank`,
  policy-approved related evidence, aggregate coverage state, relation counts, and
  whether repair was used.
- CHAT-001 owns final answer/non-answer behavior, citations, QA state transitions, and
  the final caller-owned atomic transaction.
- That final transaction must persist the final state, immutable evidence-policy
  version, ordered relation snapshot, and approved safe diagnostics. It must not
  overload `chat_model_id`, `prompt_contract_version`, `error_metadata_json`,
  citations, or mutable logs.
- Retry/history must consume the persisted snapshot. They must not rerun the verifier
  merely to reinterpret an existing completed QA result under a newer model or policy.

## Security and Privacy Boundaries

- Question and evidence excerpt are sensitive in-memory verifier inputs. They are
  excluded from `repr`, errors, logs, diagnostics, snapshots, test IDs, and final
  reports.
- The verifier prompt is context-only: assess only each supplied labelled passage
  against the exact question and emit only the strict relation schema.
- The model receives labels and text, never authority to provide source metadata,
  workspace/document IDs, paths, sufficiency, probability, or legal correctness.
- Application resolves every label to the exact immutable RAG evidence map and derives
  all identity/provenance itself.
- Raw model output is untrusted and never persisted or exposed through the Application
  result. It is either strictly parsed or discarded.
- Provider/SDK errors are translated to sanitized RAG-002 Application errors without
  chaining sensitive exception text.
- Only the existing exact local model is allowed. Missing/not-ready/incompatible model
  state fails closed before sensitive work; production remains local and has no cloud
  fallback.
- Tests and qualification data are anonymous, synthetic, and non-legal. No real
  question, document, secret, credential, `.env`, cache/model path, URI, or native
  provider object enters the repository.
- RAG-002 adds no crypto/security provider and does not weaken the existing sensitive
  payload or production fail-closed boundaries.

## Persistence, Retry, and Historical Boundaries

- RAG-002 performs no database work and never opens, commits, or rolls back a UoW.
- RAG-001 remains the authority for the retrieval run, generation snapshot, ranked
  evidence, provenance, and retrieval retry.
- A RAG-002 evaluation is in-memory and bound to one exact complete
  `RetrievalRegistration`, policy identity, exact READY verifier status, and verifier

  snapshot state fails closed.
